# 🧩 架构与实现

上一篇：[01-桥接服务部署.md](01-桥接服务部署.md)<br />
下一篇：[03-接口与SDK接入.md](03-接口与SDK接入.md)

MiCamera.Net 是连接 Miloco 原始视频接口的 .NET SDK 与桥接服务。它接收 H.264/H.265 Annex-B 视频，为同一组摄像头通道提供 RTSP 原编码直播、JPEG 截图和 H.264 WebRTC 预览。

## 🗺️ 系统全景

```mermaid
flowchart TD
    C[小米摄像头] --> M[Miloco 原始视频接口]
    M -->|认证 Cookie 与视频 WebSocket| K[MiCamera.Net 核心]
    K --> V[媒体分发与处理]
    V -->|原编码 RTP over TCP| R[RTSP 播放器]
    V -->|缓存 JPEG| A[HTTP API]
    V -->|H.264 SRTP / UDP| B[浏览器]
    B -->|同源 HTTP 信令| N[Nginx 前端代理]
    N -->|Bearer| A
    A -->|会话管理| V
    B -->|初始化与重新配置| N
    A --> S[配置服务与 SQLite]
    S -->|连接参数与摄像头列表| K
    S -->|凭据与运行配置应用| V
```

Docker 的同源代理用于 HTTP API；WebRTC 视频由桥接直接通过 UDP 发往浏览器。原生 SDK 宿主可直接暴露 API，不必使用 Docker 前端。

## 🧱 项目分层

| 项目 | 职责 |
| --- | --- |
| `MiCamera.Net.Abstractions` | 核心配置、视频块、状态、流描述、订阅接口与构建接口 |
| `MiCamera.Net` | Miloco HTTP 会话、Cookie 与证书验证，设备发现、视频 WebSocket、关键帧同步、流分发和托管生命周期 |
| `MiCamera.Net.RTSP.Abstractions` | RTSP/HTTP/WebRTC/截图/媒体配置、媒体契约和 API DTO |
| `MiCamera.Net.Media` | Annex-B 处理、访问单元与时间轴、FFmpeg 原生解码、JPEG 和按需 H.265→H.264 转码 |
| `MiCamera.Net.RTSP` | RTSP 控制与 TCP RTP 发送、HTTP API / Swagger、Bearer 校验、SQLite 配置管理、WebRTC 会话与反馈处理 |
| `MiCamera.Net.Sample.Server` | 解析基础 JSON，启用网页配置与持久化，启动控制台宿主 |
| `MiCamera.Net.Sample.Web` | React/Vite 前端，初始化与重新配置、摄像头选择、WebRTC 预览和截图；不在 Visual Studio 解决方案中 |

核心由 `MiCameraEngineFactory.CreateServerBuilder()` 建立，通过 `Initialize` 注册选项、上游会话和流监督服务。`WithRtsp` 是可选扩展，一并注册媒体、RTSP、HTTP API、Swagger 与 WebRTC；`WithWebSetup` 额外注册网页配置服务和 SQLite 存储，随后 `Build` 创建 .NET Generic Host。已有 `IHostBuilder` 可通过 `AsMiCameraServerBuilder()` 接入。

Sample 宿主使用 `Initialize → WithRtsp → WithWebSetup → Build`。核心 SDK 仍可由应用直接提供连接参数和流列表；Sample 的精简 JSON 与 SDK 选项不是同一种配置入口，接入示例见 [接口与 SDK 接入](03-接口与SDK接入.md)。

## ⚙️ 基础配置与网页配置

| 配置来源 | 内容 | 生效时机 |
| --- | --- | --- |
| `MiCameraConfig.json` | `Miloco` 的 TLS / 超时、`Streaming`、`Reconnect`，以及 `MediaServer` 的监听和媒体参数 | 后端启动时读取 |
| 网页与 SQLite | Miloco BaseUrl / PIN 认证信息、摄像头通道列表、RTSP 用户名 / 认证信息 | 保存后即时应用；重启时恢复 |
| Docker secrets | API Token 和 Miloco JWT secret | 容器启动时分别注入桥接与 Miloco |

Sample 配置加载器启用网页管理，并清空文件中旧的 Miloco 地址 / 账号 / 密码、流列表和 RTSP 凭据。用户配置以 SQLite 为准，不再从 JSON 或旧 RTSP 凭据文件恢复。

`ApplicationSettingsStore` 在一个 SQLite 事务中保存整组连接、凭据和流配置。PIN 保存为小写 MD5，RTSP 密码保存为 Digest HA1；查询接口只返回已设置标志和非秘密配置，不回传密码或摘要。数据库仍含敏感认证资料，权限和备份要求见 [部署指南](01-桥接服务部署.md)。

`WithWebSetup(dataDirectory)` 可显式指定目录，默认是`./data`目录。

数据库名为 `settings.db`。Docker 将 `/run/micamera-state` 映射到宿主的 `.deploy/micamera-state/`，与部署脚本记录 IP 的 `.deploy/settings.json` 是两份不同用途的数据。

## 👋 初始化与重新配置生命周期

首次没有已保存配置时，HTTP API 与前端可以启动，摄像头工作器等待初始化，RTSP 不监听。此时流列表为空，存活检查可以成功，完整就绪检查仍返回 503。

```mermaid
flowchart TD
    W[网页填写 Miloco 地址与 PIN] --> D[独立会话登录并发现摄像头]
    D --> C[选择通道并设置 RTSP 凭据]
    C --> V[校验参数、设备与配置版本]
    V --> P[必要时预留 RTSP 端口]
    P --> S[SQLite 事务保存新版本]
    S --> A[暂停旧播放并应用新配置]
    A --> R[恢复拉流、媒体处理与 RTSP]
    R --> M[等待收帧并验证真实画面]
```

发现摄像头使用独立认证会话，不修改正在拉流的共享会话。保存配置前再次核对 Miloco 授权、设备和通道；配置版本不匹配返回 409，避免另一页面的修改被覆盖。

保存后关闭已有 RTSP / WebRTC 播放连接，更新上游连接和摄像头工作器，恢复媒体与监听，无需重启宿主。保存完成与应用成功是两个阶段：若已提交 SQLite 但应用失败，接口返回 503，`applyPending` 为 true；网页可重试应用已保存的配置。旧流程中的自动视频就绪回退不再用于网页保存。

## 🔑 上游认证与拉流

各流拥有独立的连接、超时与重连循环，但共享一个 `MilocoSessionClient` 和 Cookie 容器。认证锁避免多路同时登录；拉流失败时会使共享认证状态失效，后续重试重新校验。

1. 调用 Miloco `/api/auth/login`，提交本地账号与密码 MD5，读取业务响应并保存 Cookie。
2. 调用 `/api/miot/login_status`，确认小米账号已授权；HTTP 200 但业务状态失败仍不能拉流。
3. 建立 `/api/miot/ws/video_stream?camera_id=设备DID&channel=通道`，HTTP/HTTPS 分别对应 WS/WSS。
4. 接收二进制 Annex-B 数据，依据配置编码识别参数集和关键帧。
5. 进入持续分发；超时、失联或处理失败后退避重连，并重新同步关键帧。

HTTP 与 WebSocket 共享同一张固定 PEM 的校验逻辑。网页通过后端配置服务调用 Miloco `/api/miot/camera_list` 发现设备，用户选择后保存为运行时流列表；部署脚本负责启动服务，不再在终端选择摄像头。

```mermaid
stateDiagram-v2
    [*] --> Authenticating
    Authenticating --> Connecting: 本地登录与小米授权成功
    Connecting --> WaitingForKeyFrame: WebSocket 建立
    WaitingForKeyFrame --> Streaming: 参数集与关键帧就绪
    Streaming --> WaitingForKeyFrame: 输入落后后重新同步
    Authenticating --> Reconnecting: 认证失败
    Connecting --> Reconnecting: 建连失败
    WaitingForKeyFrame --> Reconnecting: 关键帧超时
    Streaming --> Reconnecting: 空闲超时或断连
    Reconnecting --> Authenticating: 退避等待结束
    Streaming --> Stopped: 宿主停止
    Reconnecting --> Stopped: 宿主停止
    Stopped --> [*]
```

图中展示常见路径，API 状态以运行时值为准。不同超时的配置和退避约束见 [配置参考](00-配置文件参考.md)。

## 📦 关键帧、缓冲与视频分发

核心保留编码参数与关键帧同步状态，为每个下游提供有界订阅缓冲。新订阅者需要从可解码的随机访问点开始，不能从任意预测帧接入。数据处理落后或丢掉引用帧时，等待下一关键帧恢复，避免持续传播不可解码的视频。

媒体层将视频块整理为带时间信息的访问单元，分别广播原编码流与转码 H.264 流。缺少有效源时间信息时，`NominalFrameRate` 提供回退时钟；它不能让约 20 fps 的上游产生真实 30 fps。

RTSP 和 WebRTC 使用发送调度器吸收上游成串交付。WebRTC 的初始预留由 `PlayoutDelay` 配置，RTSP 当前初始预留为 1.2 秒；调度器遇到落后会调整等待，连续收帧后逐步恢复，过大的时间跳跃会重建锚点。缓冲能平滑部分抖动，也增加延迟，不能弥补持续缺失的源帧。

## 🎞️ 三种输出的处理路径

```mermaid
flowchart TD
    S[原始 H.264 / H.265 视频] --> U[访问单元与原编码广播]
    U --> R[RTSP 原编码直通]
    U --> K[按间隔解码关键帧]
    K --> J[原尺寸 JPEG 缓存]
    U --> C{源编码}
    C -->|H.264| H[H.264 输出]
    C -->|H.265 且有 H.264 订阅者| T[FFmpeg 按需解码和转码]
    T --> H
    H --> W[WebRTC H.264]
```

| 输出 | 编码与依赖 | 生命周期 |
| --- | --- | --- |
| RTSP | 原 H.264/H.265，RTP/RTCP over TCP；不需要 FFmpeg 解码 | 按客户端建立会话，支持 Digest 与保活 |
| JPEG | FFmpeg 原生解码器和 MJPEG 编码器；保留原尺寸 | 首次关键帧及满足截图间隔时更新缓存，请求读取最近结果 |
| H.264 源 WebRTC | 直接使用原 H.264；根据源 SPS 创建 SDP profile | 每个观看者一个 WebRTC peer，不做 H.264 再编码 |
| H.265 源 WebRTC | FFmpeg 解码并转为 H.264；根据实际转码 SPS 创建 profile | 每流共用按需转码，观看者退出后按空闲超时停止转码 |

H.265 无观看者时主要按关键帧维护截图；首次创建 WebRTC offer 也会临时订阅 H.264，以确认真实转码参数。未取得有效 SPS 时返回 503，不发布猜测的 profile。转码尺寸上限只作用于该路径，不改变 RTSP 和 JPEG。

## 📺 WebRTC 协商、反馈与恢复

服务端是 SDP offer 发起方，浏览器提交 answer 和本地 ICE 候选。服务端收集的候选通过 offer SDP 提供；没有独立的服务端候选轮询接口。具体请求见 [接口文档](03-接口与SDK接入.md)。

每流会话数受 `MaxPeersPerStream` 限制。未实际连接的会话到期回收，即使已经收到 answer；已连接会话的断连宽限期和视频媒体超时也会触发回收。停止预览应主动删除会话，不依赖超时释放资源。

媒体反馈处理包含 NACK 重传、PLI/FIR 恢复请求及 RTCP 报告。SRTP 重传缓存复用已经保护的 wire bytes，避免 RTP 序号回绕后重新加密旧包破坏安全上下文。反馈与定时恢复能改善丢包后的恢复，不构成无卡顿保证。

示例前端在已连接、页面可见且联网、用户未暂停视频时检查解码进度；约十五秒没有新解码帧会重建会话。隐藏或离线时等待恢复，用户停止预览则取消自动恢复。该能力需要浏览器加载包含恢复逻辑的前端资源。

## 🛡️ 配置、安全与部署

- JSON 文件结构由示例宿主映射到 SDK；Sample 的流列表来自 SQLite，SDK 代码配置使用 `MiCameraServerOptions.Streams`。
- 非回环 HTTP 必须配置 Bearer，所有控制器 API（含初始化、配置与健康检查）共享认证过滤器；Docker 前端代理自动附加 Token。
- Sample 的 RTSP 凭据与其他网页配置统一保存在 SQLite；SDK 自定义宿主仍可直接配置静态 Digest 凭据。
- 网页没有额外管理员登录，同源代理也能调用重新配置接口，部署应限制在可信局域网。
- HTTP 存活、完整媒体能力、RTSP 监听和真实浏览器画面是不同层次；`ready` 要求完整媒体与 RTSP 条件同时满足。
- 当前链路只提供视频、截图与浏览器预览；没有音频、录像、对讲、云台或可直接套用的公网接入流程。

主机容量、约 20 fps 的特定摄像头测量、已修复协议问题及剩余上游交付空档见 [性能记录](troubleshooting/SERVER_PERFORMANCE.md)。其中的设备条件、日期和失败结果都是结论的一部分。
