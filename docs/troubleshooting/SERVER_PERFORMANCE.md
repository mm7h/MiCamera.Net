## Web 与 VLC 并发修复（2026-10-05，中午）

已修复并部署协议侧缺陷，但不能把整条链路表述为完全流畅。用户确认同一时段米家 App 正常；后续测试仍出现摄像头到 Miloco/服务器输入路径的长交付空档。

### 确认的缺陷与修改

- RTSP Sender Report 原先将 Unix epoch 毫秒乘以 `2^32`，导致 64 位整数溢出、NTP 秒数错误。现在分别计算秒和秒内小数，并补偿当前帧的发送耗时。
- TCP 控制读取改为二进制安全解析，完整消费 `$` interleaved RTCP 和请求体；RTCP 反馈刷新会话保活。PLAY 响应先于媒体，SDP 响应头和正文原子发送，声明 Session timeout，移除不正确的 `rtptime=0`，启用 TCP NoDelay。
- RTSP 与 WebRTC 使用同一帧调度器，RTSP 初始预留 1.2 秒。跳帧或过大的正向时间戳间隔立即重建发送锚点，防止等待已丢掉的时间段而再次填满队列；恢复延迟上限为两秒。
- 实际 SIPSorcery 10.0.17 的 `SrtpContext.ProtectRtp` 使用当前 SSRC 的 OutboundRoc，每次保护序号 65535 都递增 ROC。跨回绕重新保护旧明文会改变密文/认证，反复补发 65535 还会破坏后续新包。现在在原保护委托完成后缓存完整 SRTP 密文，补发复用原始 wire bytes。按视频 SSRC、序号和时间戳匹配，保留 DTLS、安全上下文以及接收认证/防重放检查。缓存 1024 包、有效期五秒、最多重试八次。
- `MediaChecks/SrtpChecks.cs` 使用实际库、真实 UDP 发包和 AES-CM/HMAC、AES-GCM 两种模式复现失败并验证修复：跨回绕的丢包恢复、重复补发 65535、新包仍能解密、重复收到的旧包仍被防重放拒绝。RTSP 回归覆盖 NTP、分片 RTCP、请求体、保活、PLAY 顺序和突发帧调度。

### 上游定位

临时探针仅记录时间和计数，不保存画面。重启 Miloco 后原生 SDK 交付约 20 fps，但三十秒窗口仍出现约 0.47–1.13 秒 native callback 间隔；native→Python 调度通常 2–9 ms，WebSocket 发送通常 1–6 ms。同阶段真实 TCP 输入数据间隔约 0.47–1.02 秒，支持空档已发生在 WebSocket 转发之前，不能把所有暂停归因于浏览器。

SDK v0.1.7 通过局域网 TCP 直连 `192.168.3.88` / `192.168.3.90`，没有经视频云端中继；UFW inactive。两台摄像头各 50 次 ping 均无丢包，但平均延迟约 69/126 ms、最大约 552/769 ms。服务器到主路由 `192.168.3.1` 的 50 次 ping 有 4% 丢包，平均约 43 ms、最大约 604 ms；本机到服务器的 15 次 ping 无丢包，平均 2 ms、最大 15 ms。ICMP 可能被设备降优先级，这些值支持继续检查输入链路，但不能单凭它们断定路由器或 Wi-Fi 故障。服务器默认网关为 `192.168.3.100`，到两台摄像头的实际路由均为同网段 `ens18` 直连。

用户登录后只读检查主路由管理页，型号为华为凌霄子母路由 Q6 网线版，软件 `4.0.0.11(V3R2)`。用户截图确认 `.88` 和 `.90` 都在 5 GHz 联网设备列表，允许上网、未限速；截图的瞬时 `0 Kbps` 不构成断流证据。拓扑分别在 `子路由 Pro_0028` 和 `子路由_3098` 下显示一台“小米创米智能摄像机”，服务器 `.104` 在 `子路由_3097` 下；网页未提供足以把两台同名摄像机逐一对应到 IP 的详情。高级配置为自动优化信道开启、组网信道自动部署、5 GHz 带宽 `20/40/80/160 MHz`、WMM 开启，功率模式为穿墙。这些是配置允许值，不能当作实际协商带宽或实测信道。页面未显示摄像头 RSSI、协商速率、回程速率或错误统计，因此没有修改无线配置、重启或升级路由器。

随后短测中 Windows→主路由 20/20，0–1 ms；服务器→主路由 19/20，平均 1.725 ms、最大 9.684 ms，说明先前的高延迟并非持续不变。服务器 `ens18` 收发错误为零、累计 RX dropped 13 未增长；两条 SDK TCP 连接 Recv-Q/Send-Q 均为零，运行约二十分钟累计少量控制数据重传。该统计不能量化摄像头到服务器方向的视频丢包。下一项对照是将运行服务器虚拟机的主机临时直连主路由 LAN，绕过 3097 子路由回程，再做同条件 Web/VLC 并发实播；尚未完成该物理改接，不能据此认定回程为根因。

用户表示暂时无法改接网线。改为同步进行两端各 30 次探测：Windows→`.88`/`.90`/`.1` 最大延迟分别为 7/8/1 ms，均无丢包；服务器→相同三个地址最大延迟分别为 181.520/180.763/181.881 ms，`.90` 有一次未响应，其余无丢包。下一轮服务器→`.100` 最大 2.713 ms、平均 0.272 ms，服务器→`.1` 最大 88.569 ms、平均 23.676 ms，均 30/30；同时 Windows→服务器 30/30，有一次 533 ms 延迟。服务器→Windows 未收到 ICMP 响应，没有将它作为网络中断证据。该轮 `vmstat` CPU idle 88–99%、steal 0–1%、无换入换出或 I/O 等待，未发现持续资源争用。对照支持优先排查服务器外部接入路径及 3097 回程，但仍不能单凭 ICMP 确认物理链路故障，也没有证明十秒视频输入空档全部由该路径导致。未进行新的无线参数修改，绕过回程的实播对照仍待条件允许。

观察期间桥接通常使用约一核、630–666 MiB，vmstat CPU idle 约 72–81%，无持续换入换出；磁盘曾被构建缓存占满，已清理一小时以前的 Docker builder cache，释放约 14.49 GB，现有约 14 GB 可用。没有删除账户、配置、数据卷或回退镜像。恢复稳定输入后发送间隔通常约 100–123 ms、skipped=0；Miloco 重启恢复了短期输入，但未证明根治长期交付空档。临时启动探针已撤回，Miloco 恢复原来的 raw-video 启动适配器。

- 本机 Windows 的接通电源自动睡眠已禁用，最近两天未找到 Kernel-Power 睡眠事件，lastwake 为零。没有证据确认操作系统待机是触发原因；浏览器隐藏／冻结或客户端连接停止反馈的确切原因仍未证明。

### 已部署的修改

- 输入／输出队列溢出时保留已排队的连续可解码帧；丢掉引用帧后跳过后续预测帧，直到关键帧恢复。输出队列为 64 帧，能容纳发送缓冲及上游突发。旧记录中“只丢最新帧后继续预测帧”的方案已修正。
- SIPSorcery 10.0.17 的反馈对象只暴露首个 NACK PID/BLP。现在保留原有 SRTCP 认证和解密委托，在认证成功后按原始 RTCP 长度遍历全部反馈项，处理复合 NACK、序号回绕、PLI 和 FIR。视频单轨连接仍需要同时覆盖 PrimaryStream 与 VideoStream；仅覆盖一个上下文会漏掉反馈。
- RTP 帧内分成最多 20 个小批次，批次间等待 1 毫秒，为接收和补发留出时间。服务器出口抓包的约 2 万个原始 RTP 包连续有序、无漏发；尚无证据证明原发送 API 在出口制造乱序。
- 正式浏览器预览在支持 `RTCRtpReceiver.jitterBufferTarget` 的环境下设置 300 毫秒接收缓冲。它是浏览器的目标提示值，实测约 258–355 毫秒，并不能保证消除全部冻结。

Sender Report 时间映射回归已复现：SIPSorcery 10.0.17 `RecordRtpPacketSend` 把重传旧包的时间戳存成最后发送时间戳，`GetRtcpReport` 将它与报告生成时的当前 NTP 配对。新修正以新帧首次发包的 RTP/NTP 对为锚点，在原 SRTCP 加密委托前将 SR 的 RTP 时钟外推到报告 NTP；帧内 pacing 和旧包补发不更新锚点。回归覆盖真实库报告、PrimaryStream／VideoStream 两个安全上下文、时间戳回绕、其他 SSRC 以及 NTP／计数字段保持不变。该协议缺陷已确认，其对剩余浏览器冻结的影响仍需实播证明。

当前服务器配置：原始 HEVC／RTSP／JPEG 保留 4K；WebRTC 输出 1920×1080 H.264、libx264 ultrafast、2 Mbps、约一秒关键帧间隔；NominalFrameRate 为 20，发送预留缓冲为 1.2 秒。发送缓冲与接收缓冲合计约 1.5 秒，另有摄像头交付和解码延迟。1080p 上游对照没有消除长空档，已恢复 4K。没有安装或启用硬件视频加速。

本机 aiortc 1.15.0 的 `NackGenerator` 只在发现新的缺口时发送反馈，没有按定时器重复 NACK，且只保留最近 128 包的缺口。包级追踪发现 4 个未恢复包，其他补包通常在数毫秒至约 824 毫秒内到达；有少量重复包被 SRTP replay 检查拒绝。探针的重试行为可能影响结果，但没有证明它能解释全部失败，也没有修改探针阈值或把该失败作废。实际 Chrome 同条件复测仍待用户提供。

后续只在临时诊断客户端增加 100 毫秒 NACK 定时重试（生产服务与正式 `webrtc_perf.py` 均未修改），双路真实解码 180 秒复测的最终 RTP 丢包均为 0，追踪缺包全部恢复；最长帧间隔降为 554／498 毫秒，没有超过一秒的空档。客厅仍未通过原有 500 毫秒门槛。该对照支持客户端重试影响秒级失败，但不构成浏览器完全流畅或 20 fps 验收，旧失败记录仍保留。

最新 20 fps 测试继续使用该临时客户端，最终所有追踪缺包都已恢复。最慢补包分别等待约 759.5／545.5 毫秒，与 832／570 毫秒的剩余间隔相符；同期服务器完整三十秒窗口发送最大间隔约 101–132 毫秒、skipped=0、平均转码约 21–22 毫秒。结果支持补包延迟影响剩余短暂停顿，不能据此确认 Chrome 的冻结指标为零；正式探针与生产重传配置没有为了通过检查而更改。

最后一轮包含上游从约 10 fps 恢复至约 19／15 fps 的阶段，因此不能把它与之前 20 fps 输入阶段直接作同条件比较。直接读取 Miloco 原始 WebSocket 时，两路曾只有 9.91／9.83 fps，原始交付空档约 0.98／0.92 秒；随后还出现多秒空洞和卧室流关键帧超时。本机回环的 WebRTC 接收也曾出现 3.828 秒间隔，RTP 丢包为零，证明这一阶段的长空洞存在于浏览器网络之外。重建 Miloco 连接后恢复，但尚未证明上游长期稳定。灯光／夜视变化原因尚未得到用户确认，不能直接归因于夜视。

稳定阶段桥接约使用 140–170% CPU（四核总计 400%）、约 0.75–0.8 GB 内存；输入与 H.264 输出帧率相符，skipped=0，发送最大间隔通常约 110–150 毫秒。这支持编码容量足够，不能证明整条链路无冻结。Python aiortc 探针和内置浏览器仍记录过秒级空档；已请求用户在原有有线 Chrome 上刷新并复测，以核对实际预览。

## 结论更新（2026-10-03 第二次复测）

### 1. 30 fps 不可达：摄像头自身输出约 20 fps

在 Miloco 进程内挂探针读取 SDK 交付的**摄像头自身帧时间戳**（`frame_header.timestamp`，单位毫秒）与序号，样本为每 200 帧一段、共十余段：

| 通道 | 墙体时钟 | 摄像头时间戳间隔 min/mean/max | 序号增量 |
| --- | --- | --- | --- |
| living-room (1174672935) | 19.5–20.2 fps | 40–41 / 50.1 / 64–69 ms | 恒为 1 |
| bed-room (1195088663) | 19.9–20.1 fps | 40–41 / 50.0 / 65–77 ms | 恒为 1 |

序号增量恒为 1，说明**端到端没有丢帧**；摄像头时间戳间隔稳定在 50 ms 上下，说明编码器就是以 20 fps 出帧。40 ms（25 fps）或 33 ms（30 fps）的间隔从未出现，也不存在“每 5 帧丢 1 帧”（那会给出 40/40/40/40/80 的分布）。

进一步逐个画质档位验证：`MIoTCameraVideoQuality` 的取值直接决定分辨率，但**不改变帧率**。

| 请求画质 | 实测分辨率 | 实测帧率 |
| --- | --- | --- |
| 1（`LOW`） | 848×480 | 约 20 fps |
| 2（未在枚举中声明，原生库接受） | 1920×1080 | 约 20 fps |
| 3（`HIGH`，默认） | 3840×2160 | 约 20 fps |

`MIoTCameraVideoQuality` 只有 `LOW=1`、`HIGH=3`；原生库的 `videoquality` 配置项接受任意档位。结论：**该型号经 Miloco 输出的每一档都是约 20 fps，30 fps 无法通过本项目配置、`NominalFrameRate` 或画质档位获得。**

### 2. 交付方式：Miloco 到桥接的到达时刻是突发式的

摄像头出帧很规律（40–70 ms），但帧到达 Miloco 帧回调的时刻呈“突发+空洞”：同一段 200 帧内出现 5 次以上 0–5 ms 的连发，随后 150–450 ms 的空白（单次最长观察到 4.5 秒）。桥接侧 30 秒窗口的 `inputGapMax` 为 0.4–1.3 秒。因此浏览器看到的停顿主要来自**交付突发**，不是丢帧。

### 3. N100 容量：4K 输出超出预算，1080p 输出达标

用从 RTSP 直通抓取的真实 4K HEVC 样本（3840×2160，20 fps，约 580 kbps）在服务器上以 ffmpeg 实测 408 帧，参数与应用一致（libx264、ultrafast、`tune zerolatency`、baseline、6 Mbps、1 秒 GOP）：

| 链路 | CPU 时间/帧 | 单独运行吞吐 |
| --- | --- | --- |
| 仅解码 4K HEVC | 19.6 ms | 154 fps |
| 解码 4K + 缩放 1080p(fast bilinear) + x264 | 43.9 ms | 79 fps |
| 解码 4K + x264 4K 输出 | 47.5 ms | 52 fps |

两路 20 fps 共 40 帧/秒，4K 输出需要约 1.9 核，且该虚拟机实测有 6–15% steal，余量不足以吸收突发。双路实播对比：

| 浏览器输出 | `process` 均值 | `queueMax` | 每 30 秒 skipped | 解码帧率 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 3840×2160 | 40–57 ms | 1.4–2.2 秒 | 17–82 | 18.5 fps | 失败：1.2–1.9 秒停顿 |
| 1920×1080（当前） | 26–28 ms | 约 0.85 秒 | 0 | 20.07/20.09 fps | 通过：零丢包，最长间隔 0.941/0.945 秒 |

所以 1920×1080 不是保守取值，而是该主机在 20 fps 源下唯一能稳定跑满的浏览器输出上限。恢复 4K 只需把 `.deploy/MiCameraConfig.json` 的 `H264MaxWidth`/`H264MaxHeight` 改回 3840/2160，但会退回上表的失败状态。

### 4. 代码修改：输入队列满时不再整队丢弃

`CameraStreamSubscription` 原先在队列写满时清空整个缓冲并回退到等关键帧。队列深 32 帧，20 fps 下等于一次性丢掉 1.6 秒画面，再等摄像头的下一个关键帧（最多再加 1 秒），观众看到的是 2–3 秒冻结。改为**丢弃最新的这一帧**：已入队的帧仍是可解码的连续序列，消费者按自己的节奏追平，突发只损失一帧而不是整段。队列容量同时也是附加延迟的上界（32 帧 ≈ 1.6 秒）。

### 6. 浏览器面板的测量修正，以及已修复的三项缺陷

**测量修正（作废此前的浏览器结论）**：VS Code 集成浏览器面板在工具运行期间处于 `document.hidden` 状态，Chromium 会节流视频管线。用本机 canvas 生成的 20 fps 流放进同一个页面里的 `<video>`，10 秒只产出 11 帧、丢弃 10 帧。因此“浏览器只解出约 2 fps、丢弃 93/94 帧”是隐藏页节流的产物，**不能作为证据**；该结论已作废。浏览器侧数据只有在页面真正可见并出图时才有意义。可靠证据来自服务端日志与客户端侧 aiortc。

改动前可复现、且与面板可见性无关的事实：服务端 `input=19.9 fps`、`H264=20.0 fps`、`skipped=0`、`process` 7–18 ms/帧，`vmstat` 的 `us` 仅 17–23%；而浏览器发出 `nackCount=241` 时服务端 `Retransmit` 调用次数为 **0**。客户端到服务器 `ping` 平均 41 ms、最大 202 ms（正常局域网应 <2 ms）。

#### 修复 1：RTCP 反馈（NACK/PLI）从未进入重传路径

原因：本项目原来把解析器挂在 `SecureContext.UnprotectRtcpPacket` 上。用反射核对 SIPSorcery 10.0.17 后确认，该版本收到的 SRTCP 不经过这个委托（`MediaStream` 走自己的 `RtpSessionConfig`/`SrtpHandler`），所以那段代码永远不执行。改为订阅库自身的标准事件 `MediaStream.OnReceiveReportByIndex`（即 `RTCPeerConnection.VideoStream`），从 `RTCPCompoundPacket.Feedback` 取 NACK 的 `PID`/`BLP`，`PSFB + PLI` 则直接请求关键帧；同时让 `Retransmit` 不再要求已缓存密文（缓存只是优化，库会用同一序列号重新加密相同明文）。`WebRtcFeedback.cs` 及其测试随之为孤儿，已删除。

验证：一次浏览器会话从 `retransmitted 0 packets` 变为 **`retransmitted 120 packets`**。已知限制：该版本的 `RTCPCompoundPacket` 只暴露第一个 NACK FCI，一条反馈最多覆盖 `PID` + 16 位掩码共 17 个序列号。

#### 修复 2：RTP 时间轴跟随到达抖动

原因：`VideoAccessUnitClock` 原来用逐帧到达间隔作为 RTP 时长。中继把帧成串交付，串内间隔 0–5 ms、空洞处 200–1200 ms，于是时间轴在串内被压成一个瞬间、在空洞处跳变；接收端按该时钟渲染时会把整串突发判为过期。改为用 40 帧窗口的平均到达间隔推进（窗口只包含真实流逝时间，因此长期不会漂移；不足 8 个样本时仍用 `NominalFrameRate` 回退）。

验证（服务端回环、双路 130 秒、同口径对比）：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 解码帧率 | 20.07 / 20.09 fps | **20.00 / 20.01 fps** |
| RTP 丢包 | 0 | **0** |
| 最长帧间隔 | 0.94 / 0.95 秒 | **0.469 / 0.539 秒** |
| 超过 500 ms 的间隔 | 12 / 16 次 | **0 / 1 次** |

两项改动都已在 `deployment/tests/MediaChecks` 中固化为自检（10 fps 稳态不再塌缩、突发不塌缩、总时长不漂移、32 位回绕、无法重传时请求关键帧）。

#### 修复 3：发送节奏跟随到达抖动

前两项修好之后画面仍然不连续。用客户端侧 aiortc 重测 180 秒：

| 观测点 | 结果 |
| --- | --- |
| RTP 丢包 | 16491 包丢 1 包 |
| RTP 时间轴步进 | 恒为 50 ms，无缺口 |
| 帧到达间隔 | p50 39.7 ms，p90 89.9 ms，p99 268 ms，最长 350 ms，>200 ms 共 45 次/87 秒 |

局域网无丢包、时间轴无缺口、帧数完整，说明问题不在网络也不在内容，而在**交付时刻**：源侧 `inputGapMax` 每个 30 秒窗口为 261/281/322/483/532 ms，而当时是“收到即发”，源空洞被原样转交给接收端抖动缓冲，表现为每 4 秒约 2 次的 200–350 ms 冻结。

改动：新增 `VideoPlayoutScheduler`，按每一帧自带的 90 kHz 时间戳给它分配发送时隙，而不是按到达时刻；时隙整体前移一个可配置的 `WebRtc.PlayoutDelay`（默认 0.8 秒）。该延迟是吸收空洞的余量：帧比时隙晚到时立即抬高延迟（不把亏空当作一串突发补发），接收跟得上时按 5%/秒缓慢退还，因此延迟收敛到当下刚好够用的值；落后超过 2 秒视为断流，直接以配置延迟重新起拍。原来按字节节流的发送器被删除——它给一个大关键帧分配最长约 170 ms 的发送窗口，本身就超过了帧时隙。

验证（服务端发送侧、真实链路，每个 30 秒窗口一行 `WebRTC playout`）：

| 窗口 | 单元数 | 到达间隔最长 | 发送间隔最长 | 被追发帧数 | 当前延迟 |
| --- | --- | --- | --- | --- | --- |
| 2 | 600 | 62.5 ms | 62.5 ms | 0 | 800 ms |
| 3 | 600 | 60.6 ms | 60.6 ms | 0 | 800 ms |
| 4 | 600 | 69.1 ms | 69.1 ms | 0 | 800 ms |
| 5 | 601 | 62.7 ms | 62.7 ms | 0 | 800 ms |

发送间隔恒为一个帧周期（50 ms）加上 `Task.Delay` 的 1–19 ms 粒度误差，即输出已是严格均匀的 20 fps。同一批窗口里源侧 `inputGapMax` 仍高达 552 ms，说明空洞已被完全吸收。

端到端（客户端侧 aiortc，只记录 RTP 包到达、不解码，避免本地解码线程污染时间戳）：

| | 改动前 | 改动后 |
| --- | --- | --- |
| 帧到达间隔 p50 | 39.7 ms | **50.1 ms**（恰为一个帧周期） |
| p90 | 89.9 ms | **58.7 ms** |
| p99 | 268 ms | **114 ms** |
| >200 ms 的间隔 | 45 次/87 秒 | **10 次/140 秒** |

残余的 10 次（最长 460 ms）与服务端发送节奏无关（同会话 `sendGapMax` ≤ 69 ms），来自重传延迟：该会话服务端重传 282 个包，与改动前的 259 次/120 秒、327 次/180 秒同量级，不是本次改动引入的。

已知的下一个脆弱点：`VideoBroadcastSubscriber` 的订阅缓冲仍硬编码 32 帧，写满时会清空整队并回退到等关键帧——与修复 1 之前的 `CameraStreamSubscription` 是同一类悬崖。20 fps 下它需要容纳“源空洞 + 管线排队”约 15 帧，源空洞接近 1 秒时就会触顶。

#### ICE 断连与码率

画面稳定后另一个问题是观看约 30–60 秒后 WebRTC 直接断开。补上 `OnRtpClosed`/`OnTimeout`/`OnRtcpBye`/`onicecandidateerror` 与带 STUN 计数的 `oniceconnectionstatechange` 诊断后（此前只能看到一句 `connection changed to closed`，原因全丢）确认，断在 **ICE 层**而不是媒体层：浏览器 `iceConnectionState` 先 `disconnected`（实测 63.4/69.3 秒）再 `failed`，而服务端 ICE 一直是 `connected`，只是 15 秒宽限期后才删会话。断开前 STUN 双向完全正常（候选对的 `requestsSent`/`responsesReceived` 逐次配对），然后突然停止。

当时服务端以 6 Mbps 的编码目标往链路推约 3.2 Mbps、约 370 包/秒，而摄像头原始码流只有约 580 kbps。把 `H264Bitrate` 降到 2 Mbps（包率降到约 180/s）后，180 秒会话保持 `connected`，随后 3 分钟的浏览器验证也未再断开。这是纯配置改动，未重新构建。

#### 关于客户端侧差距的更正

此前把客户端侧的长间隔归因于“链路本身”并不成立。同一台 PC、真实局域网、不解码而只记录 RTP 包到达时，25450 包仅丢 3 包，时间轴无缺口；先前测到的秒级间隔来自探针自身的解码线程停顿（不解码后即消失），以及发送端当时尚未重定时。端到端结论以本节上表为准。

## 2026-10-03 追加复测：30 fps 的前提

实际摄像头高画质源已变为约 20 fps。绕过 MiCamera.Net，直接从 Miloco WebSocket 同时接收两路三分钟，分别收到 3585/3587 个视频消息，约 19.91/19.92 fps，最大收帧间隔 0.903/0.600 秒。因此当前缺少真实 30 fps 输入，不能通过改 `NominalFrameRate` 或播放速度来满足 30 fps；重复帧也不会增加运动细节。

- SDK 固定镜像中的 `MIoTCameraInstance.start_async` 默认 `HIGH`；`MIoTCameraVideoQuality` 只有 `LOW=1`、`HIGH=3`，启动参数中没有 fps。`frame_interval` 用于视觉解码抽帧，不能当作源帧率设置。
- C700（`chuangmi.camera.81ac1`）公开 [MIoT v4 规格](https://miot-spec.org/miot-spec-v2/instance?type=urn:miot-spec-v2:device:camera:0000A01C:chuangmi-81ac1:4) 未列出可写的帧率属性。`resolution-types` 是只读能力属性，不能据此写入分辨率或帧率。DeepWiki 没有索引此仓库，结论以已安装 SDK 源码及设备规格为准；这不证明所有固件/私有协议都不支持 30 fps。
- 复测前 4K 双路三分钟解码约 19.77/19.37 fps，最长帧间隔 0.719/1.477 秒，卧室一路未通过最大一秒间隔检查。同期处理通常 36–37 ms/帧；空闲阶段也观察到上游 1–3 秒间隔，不能把所有暂停归因于转码。
- 新增原分辨率 YUV420P 输入的 `av_frame_ref` 路径，避免每个 4K 帧经过 swscale 复制。需要缩放或转换格式时继续使用原转换路径，分辨率和码率配置未降低。原生 GOP 回归同时检查原尺寸和缩放后的 H.264 可再次解码。
- 本次从完整服务器源码重建镜像，境内 NuGet 源恢复依赖，复用已有基础镜像。初步实测处理时间约 29–30 ms/帧，持续验收结果见后续记录。

## 服务器与瓶颈

Ubuntu KVM 虚拟机，四个 Intel N100 vCPU、约 12 GB RAM，未发现可用的 GPU render 节点，视频靠 CPU 处理。Docker CPU 100% 表示一核，总容量约 400%。摄像头输出为 3840×2160 H.265，实际帧率曾在 20、10、15 fps 间变化，不能按配置或 SPS 中的名义帧率验收。当前测量为 15 fps。内存不是主要瓶颈，虚拟机调度与 CPU 压力需要同时观察。

已确认的主要问题：

1. **重复解码。** 固定 Miloco 镜像含完整 Python 源码。`CameraVisionHandler` 为在线摄像头自动注册视觉 JPEG，SDK 因而解码每个 4K 帧，即使没有 AI 模型或观看者。MiCamera.Net 又解码同一份视频。启动适配器关闭 Miloco 的 JPEG 注册后，其 CPU 从约 100%–180% 降至约 6%–8%，内存从约 540 MiB 降至约 150 MiB。原始视频、授权与发现保留；本部署的 Miloco 视觉图像/AI 功能关闭，截图由桥接提供。
2. **原生转码吞吐与并发。** 原版 1080p 平均处理约 51–62 ms/帧，20 fps 时超过 50 ms 预算。仅降低输出尺寸仍要解码完整 4K。帧级并行解码及减少重复截图后，1080p veryfast 实播平均约 25 ms/帧；4K ultrafast 约 25 ms/帧。但 4K veryfast 在持续负载下升至 71–75 ms/帧，产生约两秒队列积压和丢帧。4K superfast 也在后段达到约 58 ms/帧并出现停顿。短暂的 CPU 采样不能证明持续容量。
3. **RTP 丢包与恢复。** 原版 90 秒接收丢包约 1.2%，最长停顿 3.689 秒。大关键帧突发、NACK 解析不完整和未恢复时缺少新 IDR 会延长停顿。4K ultrafast 12 Mbps 单路短测通过，双路出现大量丢包及 ICE 断连；接收进程分开仍失败，因此不能只归因于一个测试进程。降低至 6 Mbps 后丢包接近零，但仍需处理偶发队列/源间隔问题。
4. **时间轴与观测不准确。** 原版 RTP 时钟按名义帧率增长，FFmpeg 时间基与 90 kHz PTS 不一致。后来发现上游 `ReceivedAt` 在入队后的分发阶段才记录，会掩盖接收队列延迟；现已改为 WebSocket 消息到达时记录并随入队数据传递。时钟漂移不是端到端延迟。

独立直连 Miloco WebSocket、绕过桥接的 120 秒测试也曾测到约 1.394/1.292 秒收帧间隔。这证明部分暂停已经存在于上游，但不能据此把所有剩余停顿都归因于摄像头或网络。

## 修改

- Miloco 使用只读启动适配器，先读取已有 secret，再关闭重复视觉 JPEG 注册及无界文件日志；不修改上游安装文件或账号数据。
- HEVC/H.264 解码启用帧级并行；按解码帧 PTS 对应回源序号和 RTP 时间戳，避免延迟输出错配到当前输入。空闲只提交关键帧并立即 drain/flush；恢复观看从关键帧开始。
- 全尺寸 JPEG 默认至少间隔五秒生成一次（`MediaServer.Snapshot.Interval`，单位秒），仍以实际解码的关键帧生成。零表示每个关键帧生成。H.264 缩放使用 fast bilinear。
- 统一编码时间基为 `1/90000`，展开 32 位 RTP 时间戳回绕；保留掉帧时间跨度。
- libx264 使用 forced-idr、重复参数集、四分之一秒 VBV；新观看者、PLI/FIR 和无法恢复的 NACK 请求 IDR，单会话限流 500 ms。
- RTP MTU 1200，约 4800 字节分批发送；缓存 512 个包，最多重试两次，有效期 1500 ms。认证/解密 SRTCP 后才解析所有 NACK 区段，适配固定库的复合 RTCP 解析限制；重传完全相同的密文字节，保留原库认证与重放检查。
- SIPSorcery 10.0.17。曾经断连的确切根因尚未证明，版本升级不是根因证据。
- 每 30 秒输出源/转码帧率、跳过数、处理耗时、队列等待、收帧间隔；新增进程 GC 停顿、分配速率及线程池统计。日志不输出凭证或 SDP。
- 新服务就绪后清理被替换的本项目容器/镜像，失败保留旧镜像；跳过被容器引用或带其他项目标签的镜像，保留卷与账号数据。
  构建前同时记录本项目容器引用的镜像 ID，覆盖标签已被其他构建移动、旧容器还在使用无标签镜像的情况；部署脚本回归检查已验证此场景。

## 实播结果

使用真实摄像头、前端 `/api` 代理和 aiortc 实际解码，不保存画面。帧间隔统计排除开始五秒；丢包、源队列跳过和解码帧间隔是不同指标。所有结果按 living-room / bed-room 顺序列出。

| 配置与时间 | 结果 |
| --- | --- |
| 原版 1080p，90 秒 | 最大停顿 3.689 秒；约 1.2% RTP 丢包，失败 |
| 720p 完整重传，180 秒，关闭重复解码前 | 最大停顿 2.755/3.106 秒，处理 48–53 ms/帧并队列丢帧，失败 |
| 540p 完整重传，180 秒 | 最大间隔 0.824/0.448 秒，短测通过；后续 600 秒仍有超过一秒停顿，失败 |
| 720p、关闭重复解码及 IDR 恢复，600 秒 | 14.96/14.92 fps；最大间隔 1.450/1.157 秒，失败 |
| 新帧级解码、1080p veryfast 4 Mbps，180 秒 | 1920×1080；14.96/14.97 fps；最大间隔 0.698/0.651 秒，零超过一秒间隔，通过 |
| 4K ultrafast 12 Mbps，单路 60 秒 | 3840×2160；14.98 fps；最大间隔 0.779 秒；RTP 残余丢包零，通过短测 |
| 4K ultrafast 12 Mbps，双路 | 收到画面但严重丢包并断连，失败；扩大接收容量及拆分接收进程仍失败 |

| 4K ultrafast 6 Mbps，旧版收帧时间，1024 包，600 秒 | 14.91/14.83 fps；最大间隔 6.019/4.936 秒，失败 |

| 当前 4K，同一摄像头新观看者晚十秒加入，各播 45 秒 | 14.97/14.91 fps；最大间隔 0.519/0.985 秒；RTP 残余丢包 0/1，两会话通过 |

测试客户端 aiortc 1.15.0 默认只重组 128 个 RTP 包；包头统计发现 4K 关键帧可达 170 个包，默认容量会丢弃完整帧并触发 PLI。其重组器遇到缺包后也不会直接跳到后续 IDR，直到缓冲被新包填满才清除旧帧：约 300 包/秒时，1024 包容量可放大成约三秒停顿。改为 256 包后，同一服务器配置的三分钟和十分钟测试通过，工具默认值相应改为 256。可用 `--rtp-buffer 128` 或 `1024` 复测差异。未放宽最大一秒帧间隔、最低帧率或尺寸检查。这个调整只影响测试客户端，不能推断真实浏览器的恢复策略。浏览器操作工具持续超时，尚未取得当前版本的浏览器画面证据；协议实际解码不等于已完成浏览器视觉验收。

当前十分钟测试同时以 `vmstat 2` 采样，平均主机 CPU 忙碌 40.7%，平均 steal 4.2%、峰值 11%，无换入换出。双路预览时桥接约占 1.7–2.1 核，Miloco 约 0.1 核；桥接内存约 943 MiB，Miloco 约 154 MiB。处理通常 25–27 ms/帧，抽查的三十秒窗口源队列跳过为零。GC 总停顿约 70–105 ms/三十秒，线程池待执行工作 0–1，没有持续 CPU 饱和或队列积压迹象。这些容量结果对应当前实际 15 fps、两路预览，不能外推到 20/25 fps 或更多独立摄像头。

最终接口回归：两路认证 RTSP 各实际解码 15 帧通过；两路 JPEG 均为 3840×2160，截图年龄小于 15 秒；未认证的桥接 API 返回 401，认证媒体就绪接口通过。检查未保存摄像头图像。Release 编译、时钟/复合 NACK/IDR 回归、当前运行 DLL 的原生真实 GOP 检查、13 项 Python 检查及 Bash 部署控制流程检查均通过。
